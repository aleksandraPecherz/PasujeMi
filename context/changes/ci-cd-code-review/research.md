# Research: CI/CD code review

**Date**: 2026-10-25T21:24:47+01:00
**Git Commit**: 327665c (czyste drzewo robocze w chwili badania; kotwice to lokalne `file:line`)
**Branch**: ci-cd-code-review

## Research Question

Na podstawie `context/changes/ci-cd-code-review/requirements.md`: co robi obecny agent (`tools/code-reviewer/`), jak wygląda (i czego brakuje w) integracji z GitHub Actions (workflow, lokalna composite action, komentarz w PR, etykiety `ai-cr:*`) oraz czy uwierzytelnienie OAuth w ramach Claude Pro (`claude setup-token`, `CLAUDE_CODE_OAUTH_TOKEN`) pasuje do ograniczenia „bez dodatkowo płatnego API". Dla otwartych decyzji: warianty i konsekwencje, bez rozstrzygania. Poza zakresem: implementacja, instalacja, generowanie tokenu, zmiany sekretów, wywołania modeli, ewaluacje promptfoo.

## Summary

- **Agent działa lokalnie, ale nie jest gotowy do CI.** Wczytuje sam diff (plik albo stdin), woła Agent SDK bez narzędzi i bez ustawień, zwraca JSON na stdout i metryki na stderr (`tools/code-reviewer/src/index.ts:23-29,36-80`). Nie przyjmuje tytułu ani opisu PR (prompt to tylko `Zrecenzuj poniższy diff.\n\n${diff}`, `index.ts:37`), mimo że `requirements.md` wymaga trzech wejść. Werdykt `fail` nie wpływa na kod wyjścia; kod 1 oznacza wyłącznie błąd wykonania lub walidacji (`index.ts:85-88`).
- **W repo nie ma jeszcze żadnej integracji z PR.** Jedyny workflow to `.github/workflows/ci.yml` (job `ci` i `smoke`, triggery `push` i `pull_request` na `master`, bez bloku `permissions`, bez composite action, bez etykiet i komentarzy). Katalogu `.github/actions/` nie ma. `tools/code-reviewer/` jest wyłączony z root `tsconfig.json` i z ESLint, więc obecny CI go nie sprawdza.
- **Uwierzytelnienie: trzy rozdzielone kategorie (sekcja 4).** (A) Potwierdzone: token z `claude setup-token` jest tokenem subskrypcji, a oficjalna akcja `claude-code-action` dokumentuje jego użycie z Pro; artykuł pomocy z 7.10.2026 mówi, że Agent SDK i `claude -p` można nadal używać „with your subscription limits", ale **nie wymienia Pro z nazwy i nie omawia CI**. (B) Niezweryfikowane: czy nasz pakiet na SDK uwierzytelni się tą zmienną na runnerze i jak zużyje limity. (C) Niejasne: warunki korzystania opisują produkty dla użytkowników i nie nazywają scenariusza „własny skrypt SDK w CI na własnym tokenie".
- **Kod w jobie z sekretem pochodzi z PR-a (sekcja 6).** Przy `pull_request` z gałęzi tego samego repo workflow, composite action, kod recenzenta, lockfile i skrypty instalacyjne zależności pochodzą z merge commitu, więc są zmienialne przez autora PR-a; zabezpieczenia modelu (`tools: []`) tego nie obejmują. Nowa decyzja D7.
- **Luki z dokumentacji zamknięte** (sekcja 3): do etykiet i komentarza wystarczy `pull-requests: write` (z `issues: write` jako alternatywą w tabeli GitHub); `secrets` nie jest dostępny w composite action i token trzeba przekazać jawnie jako input; job pominięty przez `if` raportuje „Success", a workflow pominięty w całości zostawia check w „Pending". Nadal otwarte: czy dodanie nieistniejącej etykiety ją tworzy.
- **„Bez dodatkowo płatnego API" nie jest tym samym co „bez żadnego kosztu".** `total_cost_usd` z SDK to szacunek po stronie klienta, nie rachunek. Czy extra usage jest włączone na koncie, wie tylko autorka.
- **Większość otwartych decyzji bramki to decyzje projektowe, nie braki wiedzy** (progi, „brak oceny", błąd modelu, fork, wymagany status check, model zaufania dla jobu z sekretem). Poniżej warianty i skutki, bez wyboru.

## Detailed Findings

### 1. Obecny agent `tools/code-reviewer/`

- **Zależności i środowisko.** `@anthropic-ai/claude-agent-sdk ^0.3.310` (lockfile: dokładnie 0.3.310) i `zod ^4.6.7`; `engines.node >=22`; własny `package-lock.json` w tym katalogu (`tools/code-reviewer/package.json`, `package-lock.json:23-26`). Root `.nvmrc` = 22.23.3. Skrypty: `review` (`tsx src/index.ts`) i `typecheck`. Testów dla pakietu nie znalazłem (sprawdzone: `git ls-files tools` zwraca tylko `.gitignore`, `fixtures/*`, `package*.json`, `src/index.ts`, `src/review-schema.ts`, `tsconfig.json`).
- **Wywołanie modelu** (`index.ts:36-47`): `model: "claude-sonnet-5-5"` (stała, `index.ts:7`), `tools: []`, `settingSources: []`, `maxTurns: 2`, `maxBudgetUsd: 0.5`, `outputFormat` = JSON Schema z zod. Brak narzędzi oznacza, że agent nie ma Basha ani odczytu plików, więc nie może odczytać zmiennych środowiskowych (w tym tokenu) z poziomu modelu; to wniosek z konfiguracji, nie z testu.
- **Obsługa wyniku**: wynik `subtype !== "success"` rzuca błąd (`index.ts:51-55`); `safeParse` schematu (`57-60`); osobna walidacja ocen: całkowite 1-10 (`61-66`); brak wyniku w ogóle rzuca błąd (`82`). Poprawny wynik: JSON na stdout (`68`), metryki (`total_cost_usd`, `num_turns`, `duration_ms`, `usage`) na stderr (`69-79`). Błędy też idą na stderr (`85-88`), więc stderr miesza metryki i komunikaty błędów.
- **Co się dzieje z `fail`**: schemat ma `verdict: "pass" | "fail"` (`review-schema.ts:59`), ale proces kończy się kodem 0 niezależnie od werdyktu. Bramka wymaga więc osobnego kroku, który parsuje stdout (lekcja z `context/foundation/lessons.md`: najpierw status i typ ciała, potem treść; analogicznie tutaj: najpierw kod wyjścia i `jq -e 'type == "object"'`, potem pole `verdict`).
- **Schemat** (`review-schema.ts:16-61`): sześć pól ocen jako `z.number()` bez zakresu (zakres tylko w opisie), `verdict`, `summary`. Zgodnie z `requirements.md` nazwy pól nie zmieniają się; `SYSTEM_PROMPT` (`review-schema.ts:7-12`) nie zawiera jeszcze reguł z „Code Review Criteria" ani reguł projektu (`requirements.md:199`, zmiana kontraktu jest osobna).
- **Wejścia vs wymagania**: wymagane są tytuł PR, opis PR i `git diff` względem gałęzi bazowej (`requirements.md:25-29`); agent przyjmuje dziś tylko diff (`index.ts:23-34`). Tytuł i opis to dane kontrolowane przez autora PR, tak jak diff, więc należą do tej samej klasy ryzyka prompt injection; ograniczeniem szkód jest brak narzędzi (`tools: []`), nie filtrowanie wejścia.
- **Skala wejścia**: brak limitu rozmiaru diffu w `index.ts`; granicą jest `maxBudgetUsd` i okno kontekstu modelu. Co powinno się stać z bardzo dużym diffem, to nierozstrzygnięty punkt (D5).

### 2. Obecny CI i miejsca na nowy workflow

- `ci.yml:3-7`: `on: push` i `pull_request` na `master`. Nie ma bloku `permissions:` na poziomie workflow ani jobów (domyślne uprawnienia `GITHUB_TOKEN` zależą od ustawień repozytorium; nie sprawdzałem ich, to jest dostępne tylko w ustawieniach repo). Joby `ci` (lint, `check:ui`, `astro check`, `npm test`, `build`) i `smoke` (lokalny Supabase) są niezależne od review.
- Root `tsconfig.json` ma `exclude: ["dist", "tools/code-reviewer"]`, `eslint.config.js:89` ma `globalIgnores([".claude/", "tools/code-reviewer/"])`. Skutek: istniejące kroki `lint` i `astro check` nie obejmują recenzenta. `npm run typecheck` w pakiecie jest tylko lokalny.
- Pakiet ma własny lockfile, więc job review potrzebuje `npm ci` w `tools/code-reviewer/` (z `cache-dependency-path` dla `actions/setup-node`). SDK dociąga natywny binarny Claude Code przez opcjonalne zależności npm; dokumentacja Quickstart ostrzega, że `npm ci --omit=optional` zostawia instalację bez binarki (kotwica: Quickstart, uwaga o `pathToClaudeCodeExecutable`).
- Katalogi `.github/actions/` i `.github/workflows/` poza `ci.yml` nie istnieją (`git ls-files .github` zwraca tylko `ci.yml`).

### 3. Mechanika GitHub Actions istotna dla wymagań

Źródła: [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use), [Workflow syntax → permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions) (pobrane 2026-10-25).

- **Typy `pull_request`** ([źródło](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)): domyślnie tylko `opened`, `synchronize`, `reopened`; `labeled` trzeba dodać w `types:`. Wymaganie „ponowne review uruchamia dodanie etykiety `ai-cr:review`" wymaga więc jawnego `types: [..., labeled]` i filtra po nazwie etykiety.
- **Pętle wyzwalaczy** ([źródło](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)): zdarzenia wywołane przez `GITHUB_TOKEN` nie uruchamiają kolejnych workflowów (poza `workflow_dispatch` i `repository_dispatch`). Etykieta `ai-cr:passed`/`failed` dodana przez workflow tokenem `GITHUB_TOKEN` nie wywoła ponownie `labeled`. Strona nie mówi tego wprost o etykietach, więc to wniosek z reguły ogólnej. Etykieta `ai-cr:review` dodana przez człowieka wyzwoli workflow.
- **Forki** ([źródło](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)): sekrety nie są przekazywane do runnera dla PR z forka (poza `GITHUB_TOKEN`), a `GITHUB_TOKEN` ma tam uprawnienia tylko do odczytu; PR-y Dependabota traktowane są tak samo. Skutek: dla PR-a z forka nie ma tokenu OAuth ani prawa do komentarza/etykiety, więc „pominięty review" nie może też sam zostawić śladu w PR-ze bez innego mechanizmu (D4).
- **`pull_request_target`** ([źródło](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)): działa w kontekście domyślnej gałęzi i ma dostęp do sekretów; dokumentacja ostrzega, by nie wykonywać w nim niezaufanego kodu z forka. Requirements zakładają, że nie obchodzimy ograniczeń sekretów, więc ten wariant jest poza zakresem propozycji; wspominam go tylko dlatego, że jest oczywistą „drogą na skróty".
- **Diff**: dla `pull_request` `GITHUB_SHA` to commit scalający (merge commit), `GITHUB_REF` to `refs/pull/N/merge`. Sposób zbudowania diffu względem bazy (`base...head` czy merge commit, głębokość `fetch-depth`) nie jest w dokumentacji rozstrzygnięty za nas i jest decyzją implementacyjną (D5).
- **Uprawnienia komentarza i etykiety (luka zamknięta dokumentacją)**: [tabela uprawnień GitHub](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) wymienia `POST /repos/{owner}/{repo}/issues/{issue_number}/labels`, `DELETE …/issues/{issue_number}/labels/{name}`, `POST …/issues/{issue_number}/comments` i `PATCH …/issues/comments/{comment_id}` zarówno pod „Issues" jak i „Pull requests" z dostępem `write` (kolumna „Additional Permissions" ✓, czyli wystarcza jedno z nich); odczyt komentarzy (`GET …/comments`) to `read` w obu. [Składnia workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions) podaje przykład „`pull-requests: write` lets an action add labels to a pull request" i zasadę, że po podaniu któregokolwiek uprawnienia wszystkie niewymienione dostają `none`. Wniosek (z obu źródeł łącznie): do etykiet i komentarza wystarczy `pull-requests: write`, a `contents: read` jest potrzebne tylko do checkoutu; tabela dotyczy tokenów aplikacji/PAT, a `GITHUB_TOKEN` używa tych samych nazw zakresów, ale osobnej tabeli dla `GITHUB_TOKEN` nie znalazłem. Ustawienie repo: `default_workflow_permissions` = `read` (odczyt przez `gh api repos/aleksandraPecherz/PasujeMi/actions/permissions/workflow`, 2026-10-25), czyli bez jawnego `permissions:` zapis nie jest dostępny.
- **Etykiety**: [dokumentacja REST etykiet](https://docs.github.com/en/rest/issues/labels) mówi, że usunięcie nieistniejącej etykiety zwraca 404, i że „every pull request is an issue", ale **nie mówi**, czy dodanie nieistniejącej etykiety ją tworzy czy zwraca błąd (422 opisano ogólnie jako „Validation failed"). To zostaje luką; wpływa na to, czy `ai-cr:*` muszą istnieć przed pierwszym przebiegiem (zmiana ustawień repo, której tu nie wykonujemy), oraz na to, że krok zdejmujący etykietę musi tolerować 404.
- **Composite action a sekrety (luka zamknięta dokumentacją)**: [kontekst `secrets`](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts): „The `secrets` context is not available for composite actions due to security reasons." oraz „If you want to pass a secret to a composite action, you need to do it explicitly as an input." Wejścia w composite czyta się przez kontekst `inputs`, a krok `run` wymaga `shell` ([składnia metadanych](https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax)). Skutek: token musi przejść jako `input` (lub `env` kroku wywołującego) z workflow; to nie jest zasada, której można „nie zauważyć", tylko wymóg składni. Dokumentacja nie opisuje dziedziczenia `env` kroku wywołującego przez composite, więc wybór `input` vs `env` zostaje decyzją planu.
- **Pominięte wymagane joby (luka zamknięta dokumentacją)**: [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks): job pominięty przez warunek `if` raportuje „Success" i nie blokuje wymaganego checku; natomiast workflow pominięty w całości (filtry ścieżek/gałęzi, komunikat commita) zostawia checki w stanie „Pending" i blokuje merge. Skutek dla D4: pominięcie fork-PR przez `if` na jobie zachowuje się inaczej niż pominięcie przez filtr na poziomie workflow, a „zielony" status pominiętego jobu nie jest dowodem, że review się odbyło.

### 4. Uwierzytelnienie i subskrypcja: trzy rozdzielone kategorie

Źródła pobrane 2026-10-25. Kategorie nie są wymienne: (A) to zasady, które dokumentacja stwierdza wprost; (B) to zachowanie naszego pakietu, którego nikt nie sprawdził; (C) to miejsca, gdzie tekst warunków nie rozstrzyga naszego scenariusza.

#### A. Potwierdzone zasady subskrypcji (wprost w dokumentacji)

- `claude setup-token` generuje token OAuth ważny rok, nie zapisuje go nigdzie i wypisuje w terminalu. Token „authenticates with your Claude subscription and requires a Pro, Max, Team, or Enterprise plan" i „can only make model requests". Źródło: [Authentication → Generate a long-lived token](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token).
- Kolejność pierwszeństwa: `CLAUDE_CODE_OAUTH_TOKEN` jest pozycją 5, poniżej `ANTHROPIC_AUTH_TOKEN` (2), `ANTHROPIC_API_KEY` (3) i `apiKeyHelper` (4); w trybie nieinteraktywnym `-p` klucz API „is always used when present". Źródło: [Authentication → Authentication precedence](https://code.claude.com/docs/en/authentication#authentication-precedence). Skutek: obecność `ANTHROPIC_API_KEY` w środowisku jobu przesłoniłaby token subskrypcji i przeszłaby na rozliczenie API.
- `--bare` nie czyta `CLAUDE_CODE_OAUTH_TOKEN` (to samo źródło, ostatni akapit sekcji o tokenie). Obecny agent nie używa `--bare`.
- Oficjalna akcja `claude-code-action` przyjmuje `claude_code_oauth_token` dla Pro/Max/Team/Enterprise, a „If you authenticate with an OAuth token, runs use your Claude subscription instead of API billing". Źródło: [Claude Code GitHub Actions → Manual setup](https://code.claude.com/docs/en/github-actions#manual-setup) i [→ Manage costs](https://code.claude.com/docs/en/github-actions#manage-costs). Dotyczy tej akcji, nie naszego pakietu.
- Token jest „tied to the subscription of the person who ran `claude setup-token`" ([GitHub Actions → Set up for an organization](https://code.claude.com/docs/en/github-actions#set-up-for-an-organization)).
- Użycie Agent SDK, `claude -p` i aplikacji zewnętrznych przy limitach subskrypcji, wg artykułu [Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan): aktualizacja z 7 października 2026 mówi: „You can still use the Claude Agent SDK, `claude -p`, and third-party apps with your subscription limits." (cytat przekazany przez autorkę i zgodny z treścią pobraną 2026-10-25). Ten sam wpis zapowiada, że „Claude Max and Team plans now include monthly API credits" obejmujące Agent SDK, `claude -p`, Claude API i Managed Agents. **Czego ten artykuł nie mówi**: Pro **nie jest tam wymieniony z nazwy** (ani w zdaniu o kredytach, ani w zdaniu o limitach), a **CI ani GitHub Actions nie są w nim omawiane**. Zdanie o limitach subskrypcji dotyczy więc Agent SDK i `claude -p` ogólnie; zastosowanie go do Pro i do uruchomienia w CI jest naszym wnioskiem, nie treścią artykułu. Notatka z 15 czerwca 2026 o wstrzymaniu wcześniejszych zmian jest w tym samym artykule; starsze kopie z kredytem $20 dla Pro są zastąpione i nie są obowiązujące.
- Szacunki SDK: `total_cost_usd` to „client-side estimates, not authoritative billing data" ([Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking)); `maxBudgetUsd` zatrzymuje zapytanie według tego szacunku i „can pass this value" ([TypeScript SDK → options](https://code.claude.com/docs/en/agent-sdk/typescript)).

#### B. Niezweryfikowane: działanie naszego pakietu w CI (do sprawdzenia próbą, nie lekturą)

- Czy `query()` z `@anthropic-ai/claude-agent-sdk` (wersja 0.3.310 w lockfile) na runnerze Linux odczytuje `CLAUDE_CODE_OAUTH_TOKEN` i uwierzytelnia się nim. Dokumentacja Authentication mówi, że `apiKeyHelper`, `ANTHROPIC_API_KEY` i `ANTHROPIC_AUTH_TOKEN` dotyczą „the CLI and the surfaces that wrap it, including … the Agent SDK, and GitHub Actions", ale `CLAUDE_CODE_OAUTH_TOKEN` nie jest w tej wyliczance; [Quickstart SDK](https://code.claude.com/docs/en/agent-sdk/quickstart) opisuje tylko klucz API i dostawców chmurowych. SDK uruchamia binarium Claude Code, więc dziedziczenie zmiennej jest prawdopodobne, ale to hipoteza.
- Czy zużycie z tego przebiegu jest naliczane do limitów Pro tak, jak do limitów interaktywnych (artykuł pomocy o tym nie mówi dla CI), oraz jak szybko limity Pro się wyczerpują przy typowym diffie. Jedyny punkt danych lokalnych: `tools/code-reviewer/fixtures/sample.review.metrics.json` (jeden mały, syntetyczny diff; `total_cost_usd` ≈ 0,018, szacunek, nie pomiar limitu).
- Czy na koncie Pro włączone jest dodatkowe użycie (extra usage): [Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking) wspomina o „usage credits"/extra usage dla planów płatnych; ustawienia konta są dostępne tylko autorce.
- Czy instalacja SDK w CI dostarcza natywne binarium (opcjonalne pakiety `@anthropic-ai/claude-agent-sdk-linux-x64` i `-linux-x64-musl` są w lockfile jako `optional`); [Quickstart SDK](https://code.claude.com/docs/en/agent-sdk/quickstart) ostrzega, że `npm ci --omit=optional` zostawia instalację bez binarium.
- Zachowanie `error_max_budget_usd`, `error_max_turns` i błędów uwierzytelnienia w CI (kod wyjścia, treść `errors`) jest znane z typów SDK ([TypeScript SDK → SDKResultMessage](https://code.claude.com/docs/en/agent-sdk/typescript)), nie z przebiegu u nas.

#### C. Niejasności warunków (tekst nie rozstrzyga naszego scenariusza)

- [Legal and compliance → Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use): OAuth „is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications"; deweloperzy „building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication". Zakaz dotyczy trzecich deweloperów oferujących logowanie claude.ai lub kierujących żądania przez poświadczenia Free/Pro/Max „on behalf of their users" oraz pośredniczenia w poświadczeniach. Ten sam akapit stwierdza, że nie uniemożliwia to użytkownikowi końcowemu zalogowania się własną subskrypcją do niezmodyfikowanego Claude Code.
- Ta sama strona: „Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK" ([Usage policy](https://code.claude.com/docs/en/legal-and-compliance#usage-policy)).
- [Przegląd Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) i Quickstart: „Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."
- Co z tego wynika dla nas: tekst jest napisany wokół produktów oferowanych użytkownikom. Scenariusz „skrypt na Agent SDK w CI własnego repozytorium, na tokenie właściciela konta" nie jest w nim nazwany ani dopuszczony, ani zakazany. Czy mieści się w „ordinary, individual usage", to interpretacja warunków, która należy do autorki; to badanie jej nie rozstrzyga, nie ocenia jej i nie wskazuje żadnego obowiązkowego kroku wyjaśniającego. Warianty z konsekwencjami są w D1.
- Komentarz w kodzie (`tools/code-reviewer/src/index.ts:2`) zakłada auth z lokalnego logowania i „deliberately never set" `ANTHROPIC_API_KEY`; w CI jedyną ścieżką pod ograniczeniem kosztowym jest zmienna `CLAUDE_CODE_OAUTH_TOKEN`.

### 5. Limity, koszt i trzy wielkości z requirements

- **Szacunek SDK** ([źródło](https://code.claude.com/docs/en/agent-sdk/cost-tracking)): `total_cost_usd` i `costUSD` to „client-side estimates, not authoritative billing data"; dokumentacja odradza używanie ich do decyzji finansowych. Są liczone lokalnie z wbudowanego cennika, mogą się rozjechać przy zmianie cen, nieznanym modelu lub regułach, których klient nie modeluje. Zarówno wynik sukcesu, jak i błędu zawiera `total_cost_usd` i `usage`; przy `error_max_budget_usd` `usage` pomija odpowiedź, która przekroczyła budżet, a `total_cost_usd` ją obejmuje; przy awarii sesji pola mogą być wyzerowane. Kotwica: Track cost and usage.
- **`maxBudgetUsd`** ([źródło](https://code.claude.com/docs/en/agent-sdk/typescript)): „Stop the query when the client-side cost estimate reaches this USD value. The estimate can pass this value, so leave headroom". Czyli to miękki limit oparty na szacunku, nie twarda bariera rozliczeniowa. Ma też osobny `subtype: "error_max_budget_usd"` w wyniku (TypeScript SDK, `SDKResultMessage`).
- **Faktyczna opłata a subskrypcja**: przy tokenie subskrypcji nie ma rozliczenia per token jak w API; zużycie liczy się do limitów planu. Źródło: [GitHub Actions → Manage costs](https://code.claude.com/docs/en/github-actions#manage-costs) („runs use your Claude subscription instead of API billing"). Dokumentacja cache wspomina też o „usage credits"/extra usage dla planów płatnych (Cost tracking → TTL cache): jeśli na koncie jest włączone dodatkowe użycie, wyczerpanie limitu mogłoby generować koszt. **Nie sprawdzałem ustawień konta**, więc czy extra usage jest włączone, to fakt do ustalenia przez autorkę (to jest sedno „bez dodatkowo płatnego API").
- **Zużycie limitów subskrypcji**: zob. sekcja 4.A (artykuł [Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). Aktualizacja z 7.10.2026: „You can still use the Claude Agent SDK, `claude -p`, and third-party apps with your subscription limits." Artykuł nie wymienia Pro z nazwy, nie omawia CI/GitHub Actions, nie podaje kwot kredytów i nie mówi, co się dzieje po ich wyczerpaniu. Wniosek, że ta zasada obejmuje Pro w CI, jest naszą interpretacją, nie treścią artykułu [luka B].
- **Ilość pracy na PR**: dane z `fixtures/sample.review.metrics.json` (jedna próbka, mały syntetyczny diff): 2 tury, ok. 6 s, 2648 tokenów utworzonych w cache i 741 wyjściowych, `total_cost_usd` ≈ 0,018. To jeden punkt z lokalnego przebiegu, nie miara dla prawdziwych PR-ów, i nie mówi nic o zużyciu limitu Pro.

### 6. Pochodzenie kodu wykonywanego w jobie z sekretem

Pytanie: jaki kod uruchamia się na runnerze w chwili, gdy `CLAUDE_CODE_OAUTH_TOKEN` jest dostępny, skąd on pochodzi i kto może go zmienić przed przebiegiem. Rozdzielam dwie warstwy, bo mają inne zabezpieczenia.

#### 6.1 Łańcuch wykonania przy `pull_request` (propozycja z requirements)

Dla `pull_request` „the workflow file runs from the merge commit of the pull request" ([Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)); `GITHUB_SHA` to merge commit, `GITHUB_REF` to `refs/pull/N/merge` ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). Dla `pull_request_target` workflow jest „taken from the base repository's default branch, not from the pull request" (to samo źródło). Dla kolejnych elementów łańcucha (przy `pull_request` z gałęzi tego samego repo):

| Element                                                     | Skąd pochodzi w przebiegu                                                                                       | Kto może go zmienić w PR-ze                                                                                                                                                     |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plik workflow w `.github/workflows/`                        | merge commit PR-a                                                                                               | autor PR-a (zmiana kroków, `permissions`, dopisanie `echo "$SECRET"` itd.)                                                                                                      |
| Composite action w `.github/actions/`                       | checkout merge commitu, wskazana ścieżką w `uses`                                                               | autor PR-a (to zwykłe pliki repo)                                                                                                                                               |
| Kod recenzenta `tools/code-reviewer/src/*.ts`               | checkout merge commitu                                                                                          | autor PR-a                                                                                                                                                                      |
| `package.json` i `package-lock.json` recenzenta             | checkout merge commitu                                                                                          | autor PR-a                                                                                                                                                                      |
| Instalacja zależności (`npm ci` w `tools/code-reviewer/`)   | rejestr npm, wersje i skróty z lockfile z merge commitu                                                         | pośrednio autor PR-a (zmieniając lockfile); w repo: 144 pakiety, lockfileVersion 3, wszystkie z `registry.npmjs.org` i z polem `integrity` (odczyt lokalny `package-lock.json`) |
| Skrypty instalacyjne zależności                             | uruchamiane przez npm, jeśli nie ma `--ignore-scripts`                                                          | zależą od tego samego lockfile; lockfile wskazuje 2 pakiety z `hasInstallScript`: `esbuild@0.28.2` i `fsevents@2.3.3` (to drugie opcjonalne, nie na Linuxie)                    |
| Akcje zewnętrzne (`actions/checkout`, `actions/setup-node`) | wersje wskazane w pliku workflow (dziś w `ci.yml`: tagi `@v4`, nie SHA)                                         | autor PR-a może zmienić wersję; dokumentacja zaleca przypinać do pełnego SHA ([Secure use](https://docs.github.com/en/actions/reference/security/secure-use))                   |
| Binarium Claude Code                                        | opcjonalny pakiet npm w lockfile (`@anthropic-ai/claude-agent-sdk-linux-x64`), zainstalowany tym samym `npm ci` | j.w.                                                                                                                                                                            |

Co mówi dokumentacja o skutkach:

- `npm install` i `npm run build` to przykłady poleceń, które mogą wykonać kod kontrolowany przez autora PR-a ([Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)); „The vulnerability is completed by the next step that runs code checked out into the current working directory."
- Domyślnie `npm` uruchamia skrypty cyklu życia; `--ignore-scripts` je wyłącza, a dokumentacja `npm ci` nie opisuje domyślnej polityki wprost ([npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci); strona definiuje `allow-scripts` i `strict-allow-scripts`, którego ustawienie na true przerywa instalację przy niezatwierdzonych skryptach). Zachowanie `tsx` i `esbuild` bez skryptów instalacyjnych nie było sprawdzane [luka, sprawdzalne bez sekretu].
- Dla PR-ów tego samego repo: [GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/) stwierdza, że `pull_request` z gałęzi w tym samym repo (nie z forka) dostaje sekrety, i że udostępnienie sekretów jest „safe … if the user creating the PR has write permission". To jest założenie zaufania do każdego, kto może wypchnąć gałąź, a nie zabezpieczenie techniczne: PR z gałęzi tego samego repo ma dostęp do sekretu i do zmodyfikowanych wersji wszystkich elementów z tabeli.
- Dependabot: PR-y Dependabota są traktowane jak z forka (tylko `GITHUB_TOKEN` do odczytu, bez sekretów), więc PR-y aktualizujące zależności recenzenta nie uruchomią review z tokenem ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); [Workflow syntax → permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).
- Stan repo (odczyty `gh api` 2026-10-25, tylko do odczytu): `default_workflow_permissions` = `read`; klasyczna ochrona gałęzi `master` nie istnieje („Branch not protected", 404), natomiast rulesety repozytorium nie były sprawdzane, więc nie wiadomo, czy jakieś reguły lub wymagane checki obowiązują [luka]; w repo nie ma pliku CODEOWNERS (`.github/CODEOWNERS`, `CODEOWNERS`). Dokumentacja wskazuje CODEOWNERS dla `.github` jako sposób wymuszenia zatwierdzenia zmian workflow ([Secure use](https://docs.github.com/en/actions/reference/security/secure-use)); jeśli żadna ochrona gałęzi ani ruleset tego nie wymusza, nie jest to egzekwowane (stan rulesetów nieznany). Liczby współpracowników z prawem zapisu nie sprawdzałem [luka].

#### 6.2 Zabezpieczenia modelu a zabezpieczenia runnera

| Warstwa                                                                                                                                     | Co chroni                                                                                                                                                                                                             | Czego nie chroni                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Model** (`tools: []`, `settingSources: []`, `maxTurns: 2`, `maxBudgetUsd: 0.5`, `outputFormat`; `tools/code-reviewer/src/index.ts:41-45`) | Przed tym, że niezaufany tytuł, opis lub diff nakłonią **model** do wykonania polecenia, odczytu plików lub środowiska (model nie dostaje narzędzi). Ogranicza liczbę tur i szacowany koszt. Wymusza kształt wyjścia. | Nie chroni przed kodem, który uruchamia się **przed** modelem lub **obok** niego: workflow, composite action, `index.ts`, `npm ci` i jego skrypty działają w tym samym procesie/jobie i mają dostęp do zmiennych środowiskowych kroku. Nie chroni przed sfałszowaną treścią werdyktu (prompt injection może wpłynąć na `verdict`/`summary`; to ryzyko jakości bramki, nie wycieku). |
| **Runner** (uprawnienia `GITHUB_TOKEN`, zakres, w którym sekret jest dostępny, źródło kodu, przypięcie akcji, izolacja jobu)                | Ograniczają, co może zrobić **kod** wykonywany w jobie i kto może ten kod zmienić.                                                                                                                                    | Nie chroni przed błędną oceną modelu.                                                                                                                                                                                                                                                                                                                                               |

Konsekwencja z tabeli w 6.1: przy `pull_request` z gałęzi tego samego repo osoba z prawem zapisu może zmienić dowolny element łańcucha i odczytać sekret niezależnie od tego, jak model jest zabezpieczony; zabezpieczenia modelu nie zmieniają tego wyniku. Co zabezpieczenia modelu realnie dają: model nie jest sam w sobie kanałem wycieku. Co do tego, ile ryzyka to jest w praktyce (jedno-osobowe repo vs współpracownicy), nie mam danych [luka].

Dokumentacja opisuje kilka dróg ograniczenia 6.1; stanowią one opcje w D7, nie rekomendację:

- uruchamianie w kontekście gałęzi domyślnej (`pull_request_target`: workflow i checkout z domyślnej gałęzi), przy czym PR traktowany wyłącznie jako dane, nigdy wykonywany ([Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target): „the checked-out code is only ever inspected as data and never executed");
- rozdzielenie na dwa workflow: nieuprzywilejowany `pull_request` i uprzywilejowany `workflow_run`, z ostrzeżeniem, że artefakty z niezaufanego PR-a same są niezaufane ([GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/));
- środowisko (environment) z wymaganymi recenzentami i ograniczeniem gałęzi: „These secrets are only available to workflow jobs that use the environment", a zadanie „cannot access environment secrets until approval is granted by a reviewer" ([Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments); [Secure use](https://docs.github.com/en/actions/reference/security/secure-use)). Jak reguły gałęzi środowiska działają dla `refs/pull/N/merge` nie sprawdzałem [luka];
- bramkowanie etykietą: Security Lab opisuje je jako rozwiązanie tymczasowe, nadal podatne na wyścig i zależne od ręcznej weryfikacji ([GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)).

## Architecture Insights

- Podział z requirements (workflow = wyzwalanie, uprawnienia, efekty w PR; composite action = uruchomienie recenzenta) pasuje do tego, że agent jest dziś czystą funkcją „diff → JSON": efekty uboczne (komentarz, etykieta) w ogóle nie istnieją w `tools/code-reviewer/`, więc nie ma konfliktu odpowiedzialności.

Requirements już wybierają własną composite action + własny pakiet (jako propozycję); wspominam alternatywę jako punkt odniesienia dla D1, nie jako rekomendację.

### D2. Jak rozumieć „bez dodatkowo płatnego API" operacyjnie

- A. Kryterium = brak rachunku API i brak włączonego extra usage na koncie. Wymaga sprawdzenia ustawień konta przez autorkę [luka] i zalogowania szacunku SDK tylko informacyjnie.
- B. Kryterium = także brak wyczerpania limitów Pro w normalnej pracy. Wymaga mierzenia zużycia (nie ma na to pola w wyniku SDK; `total_cost_usd` tego nie mierzy) albo ręcznej obserwacji po kilku PR-ach.
- C. Dodatkowy bezpiecznik: limit liczby przebiegów (np. `concurrency`, filtr ścieżek, ręczne etykiety zamiast każdego `synchronize`), niezależny od `maxBudgetUsd`.

Skutek: ponieważ `maxBudgetUsd` to miękki limit oparty na szacunku (D2 nie zastępuje twardego limitu rozliczeniowego), wariant A bez C nie ogranicza liczby przebiegów.

### D4. Wpływ braku oceny i błędów na bramkę oraz status dla fork-PR

Dla każdego z poniższych trzeba wybrać stan wyjścia (job fail / job success + etykieta / brak etykiety):

- **Błąd modelu, `error_max_budget_usd`, `error_max_turns`, niepoprawny JSON, brak wyniku**: dziś wszystkie to kod 1 (`index.ts:51-66,82`). Warianty: (a) job czerwony bez etykiety `ai-cr:*`; (b) job czerwony + trzecia etykieta (np. `ai-cr:error`); (c) job zielony + komentarz „review niedostępne". Konsekwencja: etykieta `ai-cr:failed` z requirements oznacza werdykt czy awarię? Przy braku rozróżnienia autor PR nie odróżni „kod słaby" od „agent padł".
- **Próg werdyktu**: model sam wydaje `pass`/`fail` (`review-schema.ts:59`); alternatywy: werdykt wyliczany z ocen (progi), albo oba z regułą „fail jeśli którykolwiek". Skutek: przy wyliczaniu z ocen konieczna jest odpowiedź z D3 dla ocen nieobecnych.
- **PR z forka**: sekretów nie ma, token jest read-only (zob. sekcja 3). Warianty: (a) job pominięty przez warunek `if` (`if: github.event.pull_request.head.repo.full_name == github.repository`); taki job raportuje „Success" (zob. niżej), więc PR z forka dostaje zielony check bez review; (b) job uruchamia się i kończy sukcesem z krokiem „skipped" w logach; (c) job kończy się neutralnie/czerwono. Konsekwencja dla ochrony gałęzi (luka zamknięta dokumentacją, [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)): job pominięty przez `if` raportuje „Success" i nie blokuje wymaganego checku (wariant a/b dałby więc zielony status bez review), a workflow pominięty w całości (filtr ścieżek/gałęzi, komunikat commita) zostawia check w „Pending" i blokuje merge. Zielony status jobu pominiętego nie jest dowodem, że review się odbyło. Czy jakiekolwiek checki są dziś wymagane, nie jest ustalone: klasyczna ochrona gałęzi `master` nie istnieje (odczyt `gh api` zwrócił 404 „Branch not protected"), ale rulesety repozytorium (i reguły na poziomie organizacji) nie były sprawdzane [luka].
- **Wymagany status check i ochrona gałęzi**: warianty: (a) bez wymagania (review doradcze), (b) wymagany tylko `ci`, review nie blokuje, (c) review wymagany. Zmiana ochrony gałęzi to ustawienie repo, nie plik; nie wykonujemy jej tutaj.

### D5. Wyzwalanie, diff i sposób komentowania

- **Typy zdarzeń**: tylko `labeled` z `ai-cr:review` (ręcznie), czy dodatkowo `opened`/`reopened`/`synchronize`/`ready_for_review`. Requirements mówią tylko, że etykieta uruchamia ponowne review; nie rozstrzygają automatycznego uruchomienia przy `opened`/`synchronize`. Konsekwencja: przy automatyzacji liczba przebiegów (D2-C) rośnie z liczbą commitów.
- **Szkice PR**: pominąć czy oceniać (oficjalna akcja do review pomija drafty; nasz workflow zdecyduje sam).
- **Zdejmowanie etykiet**: workflow może usuwać `ai-cr:review` po przebiegu (inaczej kolejna etykieta nie wyzwoli `labeled`, bo już jest) oraz stare `ai-cr:passed`/`failed` przed ustawieniem nowej. Wymaga uprawnień zapisu na etykietach.
- **Komentarz**: nowy komentarz przy każdym przebiegu (pełna historia, więcej szumu) czy aktualizacja jednego „sticky" komentarza (wymaga znacznika do jego odnalezienia i dodatkowej logiki). `summary` jest w schemacie „gotowe jako komentarz do PR-a" (`review-schema.ts:60`), ale markdown z modelu trafia do komentarza jako niezaufana treść; ryzyko jest niskie dla renderu GitHub, ale warto ustalić, czy dołączamy oceny w tabeli.
- **Budowa diffu**: `base...head` z `fetch-depth: 0` albo diff API GitHub; kontrola rozmiaru (limit znaków/plików, co robić po przekroczeniu: obciąć, pominąć pliki generowane jak `package-lock.json`, odmówić z komunikatem). Brak limitu w `index.ts` oznacza, że decyzja nie jest podjęta nigdzie.
- **Współbieżność**: `concurrency` na PR, aby dwa przebiegi (np. dwa szybkie dodania etykiety) nie nadpisywały sobie etykiet i komentarza; decyzja: anulować starszy czy kolejkować.

### D6. Zakres zmian w `tools/code-reviewer/` przed workflow: wymagane, opcje, optymalizacje

Rozdział według tego, co wynika z `requirements.md`, a co jest wyborem. Wymagane = bez tego workflow nie spełni requirements; opcje = wybór, który plan musi podjąć; optymalizacje = nie blokują.

**Wymagane (wynikają z requirements i obecnego kodu)**

- Wejścia tytuł PR i opis PR obok diffu (`requirements.md:25-29`; dziś tylko diff, `index.ts:23-37`).
- Jednoznaczny, maszynowo odczytywalny sposób odróżnienia „recenzja wykonana" od „błąd wykonania" (dziś błąd = kod 1 i komunikat na stderr, `index.ts:85-88`).
- Osobna bramka, która czyta `verdict` z JSON-a na stdout: kod wyjścia 0 dla poprawnie wykonanej recenzji z `verdict: "fail"` jest dopuszczalny, o ile bramka obsługuje werdykt (kod 0 przy `fail` nie jest błędem recenzenta, tylko podziałem odpowiedzialności). Bramka musi sprawdzić kod wyjścia i typ/kształt JSON-a przed odczytem pola (lekcja z `context/foundation/lessons.md`).
- `npm ci` w `tools/code-reviewer/` (własny lockfile) przed uruchomieniem.

**Opcje (wybór należy do planu; zależą od D3, D4, D7)**

- Gdzie żyje logika bramki: w pakiecie (kod testowalny) albo w wrapperze bash w composite action (bez testów; zob. lekcja o weryfikacji statusu/typu przed treścią).
- Czy `verdict` ma być także odzwierciedlony kodem wyjścia (np. osobny kod dla `fail`) zamiast samego JSON-a; oba podejścia są dopuszczalne, jeśli bramka jest jedna i jawna.
- Rozdzielenie metryk od komunikatów błędów (dziś oba na stderr): osobny plik/output albo zostawić.
- Objęcie pakietu `typecheck`em w CI (dziś poza root `tsconfig.json` i ESLint) i testy pakietu (dziś ich nie ma).
- Limit rozmiaru diffu i zachowanie po jego przekroczeniu (zob. D5).

**Optymalizacje (nie blokują)**

- Cache `npm ci` dla podkatalogu (`cache-dependency-path` w `actions/setup-node`).
- Osobne wpisywanie `usage`/`modelUsage` do podsumowania jobu.
